# Webhook security: signatures and egress

Two things protect a webhook. The signature lets the merchant prove a delivery came from
Clearinghouse and is recent. The egress path protects Clearinghouse from the merchant,
because a webhook URL is a URL an outsider chose and Clearinghouse will POST to.

Sources that shaped this note:

- Stripe's webhook docs, https://docs.stripe.com/webhooks (sections "Verify webhook
  signatures manually", "Preventing replay attacks" and "Roll endpoint signing secrets"),
  and the troubleshooting page https://docs.stripe.com/webhooks/signature.
- The `stripe/smokescreen` README, https://github.com/stripe/smokescreen.

## Signatures

Code: `lib/clearinghouse/webhooks/signature.rb`, `lib/clearinghouse/webhooks/secret_rotation.rb`,
`clients/go/webhooksig/`. Vectors: `spec/fixtures/signatures.json`, generated by
`bin/gen-signature-vectors`.

```
Clearinghouse-Signature: t=1700000000,v1=<hex HMAC-SHA256(secret, "1700000000." + raw body)>[,v1=...]
```

This is Stripe's scheme with our header name. The timestamp is part of the signed string,
so an attacker who captures a delivery cannot re-date it, and the verifier's tolerance
bounds how long a captured delivery can be replayed. Stripe's docs put it as "because this
timestamp is part of the signed payload, it's also verified by the signature".

### Parsing rules

Every verifier has to make the same call on the same header, or a vector passes in Ruby
and fails in Go. These are the rules, and each one has a vector.

| Input | Decision | Why |
|---|---|---|
| Elements split on `,`; spaces and tabs around an element are ignored | accept | Stripe's libraries split on `,\s*`. Only space and tab, not `String#strip`'s NUL and newlines. |
| Unknown keys (`v0`, `v2`, anything not `t` or `v1`) | ignored | Stripe: "You can discard all other elements." Stripe itself sends a fake `v0` on test events. A matching `v0` does not count. |
| No `t`, or no `v1` | `malformed_header` | Nothing to check. A header with only `v0` has no `v1`. |
| Two `t` elements, even equal ones | `malformed_header` | "Last one wins" and "first one wins" are both plausible and would diverge across implementations. Refusing is the only unambiguous answer. |
| `t` not 1 to 15 ASCII digits (empty, `abc`, `-1`, `+1`, `1.5`, 16 digits) | `malformed_header` | 15 digits keeps every implementation inside int64 without overflow handling. Leading zeros are allowed, and the signed string uses the timestamp text exactly as sent. |
| Empty `v1=`, even next to a valid one | `malformed_header` | An empty signature is never produced by a signer, so it means the header was mangled. |
| Empty element (`,,`, trailing comma), element without `=`, empty key | `malformed_header` | Strict grammar is cheaper to keep identical in two languages than a lenient one. |
| Keys are case-sensitive (`T=`, `V1=`) | ignored as unknown, so usually `malformed_header` | Matches Stripe. |
| `v1` in uppercase hex | `no_matching_signature` | Signatures are compared as the lowercase strings the signer emits, as Stripe's libraries do. Accepting both cases would be harmless, but "compare the bytes" is one rule instead of two. |
| `v1` of the wrong length or not hex | `no_matching_signature` | It is a signature, just not a right one. |
| Several `v1`s | valid if any one matches any secret the verifier holds | This is what makes rotation work. |

The signature is checked **before** the timestamp, the order Stripe's libraries use. A
forged header with a stale timestamp reports `no_matching_signature`.

### Tolerance

- Reject when `|now - t| > tolerance`, in **both** directions. Stripe's libraries only
  reject old timestamps. A timestamp from the future is either clock skew or a delivery
  pre-signed for later replay, and bounding it costs nothing.
- The boundary is **inclusive**: exactly `tolerance` seconds old or ahead passes. That is
  what Stripe's `timestamp < now - tolerance` check does on the old side, and the future
  side mirrors it.
- Default 300 seconds, Stripe's default.
- Stripe warns that a tolerance of 0 disables their check. Here 0 means "exactly now" and a
  negative tolerance raises. There is no way to turn the check off by accident.

### Constant-time comparison

Each candidate `v1` is compared against the expected MAC for each secret with
`OpenSSL.fixed_length_secure_compare` in Ruby and `hmac.Equal` in Go. The Ruby side checks
lengths first, since `fixed_length_secure_compare` raises on unequal lengths; returning
early on a length mismatch only reveals that the candidate is not 64 characters, which the
attacker chose. A spec asserts the secure compare is actually called.

### Bytes, not strings

The MAC is over raw bytes. Ruby forces the payload and timestamp to binary before
concatenating, so a UTF-8 payload and the same bytes tagged binary sign identically, and a
header that is not valid UTF-8 does not raise. Stripe's troubleshooting page is mostly
about frameworks that re-serialize or re-encode the body, and the vectors include a
unicode payload, a trailing newline, an empty body, and a receiver that stripped the
trailing newline (which must fail).

### Secret rotation

`SecretRotation` holds a current secret and optionally a previous one with an expiry. It is
a pure value; persistence arrives with the webhook endpoints table.

- `rotate(new_secret:, now:, overlap:)` makes the new secret current and keeps the old one
  signing until `now + overlap`. Overlap is 0 to 24 hours, as with Stripe's "roll secret",
  which lets the merchant "delay its expiration for up to 24 hours".
- During the overlap every delivery carries one `v1` per active secret, current first. A
  merchant that has deployed either secret verifies.
- The previous secret is live strictly before its expiry. At the expiry instant only the
  current one signs.
- At most two secrets are live. Rotating again mid-window drops the older previous secret
  immediately. Supporting a chain would make every delivery's header grow with how often
  the merchant panics, and two is what Stripe's UI offers.
- Secrets are `whsec_` plus 32 random bytes, url-safe base64. The whole string is the HMAC
  key, prefix included, which is how Stripe's own libraries treat `whsec_` secrets.

### The shared vectors

`spec/fixtures/signatures.json` is the contract with RiskGate's verifier and with
`clients/go/webhooksig`. The shape is fixed:
`[{name, secrets, payload, header, now, tolerance, valid, error}]`, where `secrets` are the
secrets the **verifier** holds.

Valid headers are produced by the Ruby signer through `bin/gen-signature-vectors`. The
malformed ones are written by hand, since the signer cannot produce them. A spec runs the
generator with `--check`, so the file cannot drift from the script. Because the vectors
come from the same code they test, four were checked independently with the openssl CLI,
and one more MAC is pinned in `signature_spec.rb` the same way:

```
$ P='{"id":"evt_1","object":"event","type":"payment_intent.succeeded","created":1700000000,"api_version":"2026-09-01","data":{"object":{"id":"pi_1","object":"payment_intent","amount":1000,"currency":"usd"}}}'
$ printf '%s' "1700000000.$P" | openssl dgst -sha256 -hmac whsec_test_clearinghouse_single_secret
SHA2-256(stdin)= 73c12667ff0445ec4d478aa5851a10463a1a2b01248dc68eac5f1cc63e1c58da      # valid_single_secret
$ printf '%s' '1700000000.{"description":"café 東京 💳"}' | openssl dgst -sha256 -hmac whsec_test_clearinghouse_single_secret
SHA2-256(stdin)= 5bd95f737909e532d38b8ed52e07fd42ac7fe909a6030508e5927f809122c609      # unicode_payload
```

Each matches the `v1` in the file.

### The Go verifier

`clients/go/webhooksig` is the reference verifier for Go consumers: its own module
(`github.com/Sanjith-Shan/Clearinghouse/clients/go`, Go 1.23), standard library only.
RiskGate keeps its own verifier; both pass the same vectors.

- `Verify(payload, header, secrets, now, tolerance) error` returns `nil` or one of the
  sentinel errors `ErrNoMatchingSignature`, `ErrTimestampOutsideTolerance`,
  `ErrMalformedHeader`, whose messages are the vector error codes. Caller mistakes (no
  secrets, an empty secret, a negative tolerance) return `ErrInvalidArgument` instead of
  panicking, so a misconfigured consumer can answer 500 rather than 400.
- The comparison is `hmac.Equal` on the hex strings.
- `go test` reads `../../../spec/fixtures/signatures.json` and runs every vector as a
  subtest, rejecting unknown JSON fields so a shape change fails loudly. `FuzzVerify` uses
  the vectors as its seed corpus and checks that no header panics and that `Sign`'s output
  always verifies. A 20-second local fuzz run (about 3.5 million executions) found nothing.
- `Example` shows the handler shape: verify the raw body before decoding it.

## SSRF guard and egress

Code: `lib/clearinghouse/webhooks/safe_http.rb` and `lib/clearinghouse/webhooks/egress/`.

A merchant chooses the URL, and Clearinghouse POSTs to it from inside its own network.
Without a guard, `https://169.254.169.254/latest/meta-data/` fetches cloud credentials and
`https://10.0.0.5:5432/` probes the database. Stripe's answer is Smokescreen, an egress
proxy that "resolves each domain name that is requested, and ensures that it is a
publicly routable IP address and not an internal IP address", which "prevents a class of
attacks where, for instance, our own webhooks infrastructure is used to scan Stripe's
internal network". Clearinghouse is one process, so `SafeHttp` does the same job in-line
instead of as a proxy. The README also warns that its hostname ACL "is only applied to
hostnames as they appear in the request" and recommends blocking by resolved IP. That is
the design here: the hostname is only ever used to look up addresses, and the decision is
made on the addresses.

### The pipeline

1. **Parse strictly** (`Egress::Target`). https only. `http://` is allowed for exactly
   `localhost` and `127.0.0.1`, and only when `test_mode: true` is passed, so the test
   suite can deliver to a local server. Refused before any DNS lookup:
   - userinfo (`https://hooks.example@127.0.0.1/` is a classic parser-confusion trick);
   - any IPv4 spelling other than four canonical decimal octets. The rule is WHATWG's:
     if the last label of the host looks like a number (`[0-9]+` or `0x...`), the host is
     an IPv4 address, and then it must be a dotted quad with no leading zeros. That
     catches `2130706433`, `0177.0.0.1`, `0x7f.0.0.1`, `0x7f000001`, `127.1`, and
     `127.0.0.01`, all of which some resolver or `inet_aton` would read as 127.0.0.1;
   - percent-encoded hosts, non-ASCII hosts (IDNs must arrive as punycode; Smokescreen's ACL
     likewise only takes punycode hosts), empty labels, a trailing dot, IPv6 zone IDs, whitespace and control
     characters anywhere, ports outside 1 to 65535, URLs over 2048 bytes.
2. **Resolve once** through an injected `Egress::Resolver`. Production uses
   `SystemResolver` (getaddrinfo with a timeout). A URL with a literal address skips DNS.
3. **Check every address** (`Egress::IpPolicy`). If any address is internal, the delivery
   is `Blocked`, even if another is public. Picking the public one would work today and
   hand the attacker a coin flip tomorrow.
4. **Connect to the checked address.** `Net::HTTP.new(hostname, port, nil)` plus
   `http.ipaddr = checked_ip`. In net-http 0.4.1 (Ruby 3.3), `connect` opens the TCP socket
   to `@ipaddr || address`, while SNI (`s.hostname = @address`), the certificate hostname
   check (`post_connection_check(@address)` and `verify_hostname`) and the `Host` header all
   use the hostname. I read that in the net/http source, and the integration spec proves
   it against a local TLS server: the server sees SNI `hooks.merchant.test` and
   `Host: hooks.merchant.test:<port>` on a connection made to 127.0.0.1, and a certificate
   for a different name fails with `hostname mismatch`. I also ran one delivery by hand to
   httpbin.org on 2026-09-23 to see it work against a public CA chain (not part of CI).
   The third argument `nil` matters: the default `:ENV` would honour `https_proxy`, and
   the connection would go wherever the proxy sends it. A spec sets `https_proxy` and
   checks the connect still goes to the pinned address.
5. **Send, bounded.** Connect and TLS handshake are bounded by `connect_timeout`, each
   read and write by `read_timeout`, and the whole exchange by `total_timeout`. The body is
   read up to `max_body_bytes` (64 KiB by default) and then abandoned. `Accept-Encoding:
   identity` so the cap counts wire bytes and there is no decompression to bomb.
6. **Never follow redirects.** Net::HTTP does not, and a 3xx is `Rejected(status)`. Stripe's
   docs likewise treat a redirect response to a webhook as a failure.

The outcome is one of `Delivered(status, body)`, `Rejected(status, body)`,
`Timeout(phase)`, `ConnectionFailed(message)`, `Blocked(reason, detail)`. `post` never
raises for anything DNS or the remote end can do. `Blocked` should not be retried; the
others go through the delivery retry schedule. `pin(url)` runs steps 1 to 3 without
sending, for refusing a bad URL when the merchant registers it. `post` checks again at
send time, since DNS can change in between.

### DNS rebinding

The bug: resolve the name, check the address, then give the name to the HTTP client,
which resolves it again. An attacker's DNS server answers the first query with a public
address and the second with 127.0.0.1 (TTL 0), and the request lands on an internal
service. `safe_http_spec.rb` has a fake resolver that does exactly this and a fake network
in which connecting by name resolves through that same resolver, as the OS would. The
spec contains a naive "check, then `Net::HTTP.start(hostname)`" client as the
counterexample, and shows that it resolves twice, connects to 127.0.0.1 and receives the
internal server's response. `SafeHttp` against the same resolver resolves once, connects
to the public address, and the internal server receives nothing.

### Address policy

IPv4 is a deny list of the IANA special-purpose ranges: 0.0.0.0/8, 10/8, 100.64/10
(CGNAT), 127/8, 169.254/16 (link-local, including the metadata service at
169.254.169.254), 172.16/12, 192.0.0/24, the three documentation /24s, 192.88.99/24,
192.168/16, 198.18/15, 224/4 (multicast), 255.255.255.255 and 240/4.

IPv6 is an allow list with holes: only global unicast (2000::/3) and NAT64 are allowed,
so `::`, `::1`, fc00::/7, fe80::/10, fec0::/10, ff00::/8 and 100::/64 are refused, each
with its own reason, and so is anything a future RFC carves out below 2000::/3. Inside
2000::/3, 2001::/23, 2001:db8::/32 and 3fff::/20 are refused.

Addresses that carry an IPv4 address:

| Range | Decision | Why |
|---|---|---|
| IPv4-mapped `::ffff:0:0/96` | always refused, the log names the embedded address | No public AAAA record holds a mapped address. On a dual-stack socket it reaches the embedded IPv4 address, so `::ffff:127.0.0.1` is loopback. Refusing the whole range is simpler than checking the embedded address and loses nothing. |
| IPv4-compatible `::/96` | always refused | Deprecated by RFC 4291. |
| NAT64 `64:ff9b::/96` | judged by the embedded address | On an IPv6-only network with DNS64 every IPv4 site appears under this prefix, so refusing it outright would break delivery there. `64:ff9b::a9fe:a9fe` (169.254.169.254) is refused as `nat64_link_local`. |
| Local-use NAT64 `64:ff9b:1::/48` | refused | Site-specific by definition (RFC 8215). |
| 6to4 `2002::/16` | judged by the embedded address (bits 16 to 47) | `2002:7f00:1::1` routes towards 127.0.0.1. |
| Teredo `2001::/32` | refused, inside 2001::/23 | Obfuscated embedded addresses, and deprecated. |

### What this does not cover

- Only the first checked address is tried. A merchant with several A records and one
  dead host sees failures that a happy-eyeballs client would avoid. Easy to add later
  (walk the checked list), and it must stay the checked list.
- `total_timeout` uses `Timeout.timeout`, which interrupts the thread from outside. That is
  the usual objection to it, and I accept it here because Net::HTTP already uses the
  same mechanism for `open_timeout`, and nothing else bounds a server that drips one
  header byte just inside every read timeout. The integration spec has that server.
- Ports are not restricted. The address policy is what stops internal access; a port
  allow list would mostly break merchants on 8443.
- No hostname allow or deny list. Smokescreen has per-role ACLs because many services
  share it; Clearinghouse has one egress user, webhooks, which may go anywhere public.
